# Durable scoped revocations

The opt-in `./revocations` RevocationRegistry uses the pinned Evidence persistence SDK dce7105a70b42d77afe4cd48d34723331447037c in Identity's **own operational database**, never another engine's database. It provides one project-scoped aggregate: policy revision (starting at one), actor revocation epochs (starting at zero) and exact revoked capability IDs. All changes are monotonic. There is no removal/reset, key/token storage, issuance, member provisioning, dynamic administrator editing, network endpoint or publication route.

Trusted host configuration fixes a bounded administrator list. Every administrative call requires an authenticated, scoped, listed human with current owner authority before cached responses can be returned. Recreate the registry after configuration/administrator changes. This list and the incoming Context are host trust boundaries, not identity proofing. Lost-acknowledgement replay returns a historical command receipt, never current authority; read or verify again for current state. Expected revisions, shared project serialization, immutable revisions and atomic audit/outbox protect changes. Allowed command replays add a checked-command audit without repeating change/outbox effects. Denied transactions roll back.

`initialize(context, commandId)` can create state once; a new command cannot reset it. `apply(context, expectedRevision, command, commandId)` accepts exactly advance-policy, advance-actor (actorId), or revoke-capability (id). Revisions are safe integers; actor entries cap at1024, capability IDs at4096, aggregate at1MiB. IDs are at most128 characters. Exhaustion denies rather than evicting revocations. Future bounded compaction needs a separately designed durable protocol.

`verify(context, token, {action, resourceId}, secret)` repeats current role/scope authorization and obtains current revocation state under the same lock as administration. The trusted live clock is sampled after that load, rejecting expiry or clock regression despite an old request timestamp. The existing HMAC capability primitive verifies signature/audience/purpose/resource/revision/epoch/revocation. A bounded exact capability profile and maximum one-hour validity are checked before returning. Context/expected values/key bytes are captured before awaits; copied key bytes are zeroed afterwards. Keys remain deployment-managed, and tokens/signatures/key bytes never enter SQL or audit payloads. The caller's key buffer is retained unchanged.

A returned capability is a verified snapshot, not a transferable one-shot execution permit. The Identity transaction does not atomically fence an action in another engine, processor, database or network service. Gateways must query current authority at the point of use, refresh incoming identity/roles through qualified host authentication, and separately prevent dispatch/publication without authorization. Existing signed capabilities bind actorId but not actor kind; the host must maintain unique actor IDs across kinds within scope. Epoch changes conservatively invalidate every principal sharing that ID. This module does not repair ambiguous identity mappings or change the original capability API.

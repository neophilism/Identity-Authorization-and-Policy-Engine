# Revocation tests over PostgreSQL sessions

`npm run test:postgres` runs the actual pinned SDK PostgreSQL driver/canonical migration and RevocationRegistry over separate authenticated TCP sessions on a disposable PostgreSQL17 CI service. It is separate evidence from embedded PGlite. Five groups cover: competing revision changes; verification denied after an observed lock wait followed by committed revocation; expiry advanced only after an observed lock wait; committed revocation after lost acknowledgement/fresh pool without repeated effect; and migration/admin/runtime-role/schema/scope isolation.

Tests require `IAP_TEST_DISPOSABLE_POSTGRES=1` and `IAP_TEST_ADMIN_URL` for an empty loopback database named `identity_ci`, migration username postgres, without URL query/fragment overrides. Existing ledger state causes rejection. The fixture never resets a database. The SDK transaction owns BEGIN/COMMIT while every canonical migration statement is retained. Fixed fixture passwords are not deployment credentials. Application calls use a non-owner authenticated LOGIN with only evidence_runtime membership; distinct backend PIDs and session_user are asserted. Migration and lowered-administrator sessions cannot run the service.

The two lock cases use pg_stat_activity wait_event_type=Lock plus pg_blocking_pids through an independent fixture-admin connection. Clock advancement waits for observed database blocking, rather than inferring contention from a sleep or query mock. A direct fixture-only revocation write occurs while the same SDK project lock is held; it is not another administrative API. Pool cleanup is idempotent and releases lock gates even on failures.

## Resource-policy session extension (PR13)

Seven additional network groups use the accepted public resource-policy and membership APIs. Three groups start with an allowed researcher and hold a real `setResourcePolicy` transaction immediately before COMMIT, then require independently observed `pg_stat_activity` Lock/nonempty blocking PIDs for `resolveResource` before committing member, purpose or action restrictions. Two further groups hold real public member disable/demotion commands likewise and deny that resource-aware resolution. The reader claims forged owner roles; the allowed baseline must return stored researcher roles. Both the blocked call and a fresh pool must observe the appropriate denial after the change commits.

Another group holds a real public membership demotion of the original owner before COMMIT. A cached `setResourcePolicy` acknowledgement must wait and then deny, preserving the resource registry. The final group holds a winning resource-policy change, independently observes a same-revision contender blocking, then commits while losing only the winning acknowledgement. The contender conflicts; a fresh pool recovers the exact winning edition, retains exact original policy editions1/2 and the original historical acknowledgement without reviving access, and observes exactly two resource record revisions/change outbox entries and a valid audit chain.

The original canonical migration, explicit empty disposable loopback `identity_ci`, restricted authenticated LOGIN, distinct backend PIDs, independent observer and no-reset fixture are unchanged. No resource-policy or membership fixture SQL mutation is used by these seven new cases. Exact owning-history reads and outbox inspection are fixture assertions, not new public admin routes.
